[6] pagedlod.go:242 tileTriangles 仅按 XY 质心分块
    问题: 陡峭地形/崖壁/悬垂结构的三角形按水平投影错分, 同一瓦片内可能
          混入垂直方向相距很远的几何, 导致包围球虚大、LOD 切换阈值失真。
    决策: 不改变分块归属。XY 分块是 Smart3D/S3C 的瓦片寻址约定, 改成
          八叉树会破坏与既有查看器/命名体系的兼容性, 风险远大于收益。
          因此本项按"可诊断化"处理, 而非改变算法。
    修复: 新增 tileZSpread(mesh, bounds, tiles, gridX, gridY), 计算所有
          非空瓦片中"瓦片 Z 跨度 / 瓦片水平footprint"的最大比值:
            <= 1  表示瓦片内地形基本平坦, XY 网格适配良好
            >> 1  表示存在高大垂直结构(崖面/建筑立面/悬垂), 单个瓦片
                  的垂直跨度远大于地图投影footprint, 包围球会虚大,
                  进而使 PagedLOD 切换阈值偏大、粗层级停留过久
          buildSmart3DOSGB 在比值 > 1 时向任务日志输出一条说明, 让该
          情况可见可查, 而不是默默产出切换行为异常的树。
          该值为诊断信息, 不置任务失败, 不改变产物。
    实测验证: 平面网格比值 = 0; 注入一个 z=100 的垂直墙后比值 = 25.00。
    新增测试: TestTileZSpreadFlatAndSteep, TestTileZSpreadEmptyInputs。
    后续可选(未做): 若需真正改进, 可对 Z 跨度超阈值的瓦片做二次竖直细分,
          或改用八叉树并按 S3C 兼容命名输出; 属独立特性, 不在本次范围。
    状态: [x] 已完成

[7] pagedlod.go:308 simplifyMesh 为顶点聚类, 无边界保护
    问题: 聚类简化在瓦片边界处自由移动顶点, 相邻瓦片各简各的, 产生裂缝;
          且 L0(1/16 面)在低面数瓦片上会退化为几乎无几何。
    实测证据(新测试 TestSimplifyWithoutToleranceMovesBoundary):
          16x16 平面网格, 原始包围盒 [0,0]-[16,16], 容忍度=0 时简化后
          变成 [1.5,1.5]-[14.5,14.5] —— 边界向内收缩 1.5 个单位,
          相邻瓦片各收缩各的, 就是裂缝的直接来源。
    修复: 新增 simplifyMeshPreservingBoundary(src, targetFaces,
          boundaryTolerance), 把位于包围盒边界带内的顶点"锁定":
          不参与聚类、位置保持原样(每个锁定顶点自成一个单元素簇,
          质心计算天然等于自身)。simplifyMesh 保留为薄封装(默认 0 容忍),
          不破坏既有调用与测试。
          新增 helper tileBoundaryTolerance(mesh) = 包围盒最大边长 / 64,
          由瓦片自身尺度推导, 因此对米/英尺/OpenMVS 局部坐标都自适应;
          退化(零尺寸)网格返回 0 即自动关闭锁定。
          buildSmart3DOSGB 的 L1/L2 两级简化均改为调用新函数。
    过程中发现并修复的次生缺陷:
          最初实现无条件对 X/Y/Z 三轴做边界判定, 但平面瓦片(z 全等)
          的每个顶点都同时落在 Z 的两个面上, 导致整个瓦片被全部锁定,
          简化完全失效(实测 512 面 -> 512 面, 零简化)。
          已改为仅对"网格在该轴确有延展"的方向生效
          (lockX/lockY/lockZ = 该轴长度 > 容忍度)。
          修复后实测: 2048 面网格 target=256 时得 254 面, 且边界不变。
    新增测试: TestSimplifyPreservesBoundary(边界不变 + 面数确实下降),
          TestSimplifyWithoutToleranceMovesBoundary(记录旧行为),
          TestSimplifiedMeshStillTiles(简化后分块不丢面),
          TestTileBoundaryToleranceDegenerate(空/单点网格返回 0)。
    状态: [x] 已完成

[19] tokenize 把 Windows 反斜杠路径当转义符, 静默corrupt路径 (新发现)
    位置: main.go tokenize()
    问题: 原实现只要遇到 '\' 就置 escaped=true 并吞掉下一个字符, 因此
          `-o "C:\data\job\out.mvs"` 被解析成单个 token
          `C:datajobout.mvs` —— 反斜杠全部丢失, 路径彻底损坏。
          由于 .env.example 与 Dockerfile 中的默认值全部使用正斜杠
          (OSGCONV_BIN=E:/...) 或裸命令名, 该缺陷被长期掩盖; 但任何用户
          按 Windows 习惯粘贴 `E:\OpenSceneGraph-3.6.5\bin\osgconv.exe`
          都会中招, 且错误表现为"工具写到了奇怪的位置", 极难定位。
    实测证据: tokenize(`tool -i "C:\data\job"`) 修复前输出 `C:datajob`。
    修复: 改为"仅在下一字符确实特殊时才转义"的规则:
          - 单引号内完全字面量
          - '\' 仅当后跟 " \ ' 空格/Tab 时才作转义(保留 \" 与 "\ " 语义)
          - 其余情况(如 C:\data 中的 '\')原样保留
          - 行尾孤立 '\' 原样保留
          修复后 `C:\data\job\out.mvs` 完整保留; UNC、含空格路径、
          混合分隔符均正确。
    已知限制(诚实记录, 非本次引入): `"C:\dir\"` 这种"引号前紧邻
          反斜杠"的写法与转义引号本质歧义, 旧实现同样会误吞右引号并报
          unterminated quote。已用测试
          TestTokenizeTrailingBackslashBeforeQuoteIsAmbiguous 固化该行为,
          避免误认为是回归。
    新增测试 8 个: TestTokenizePreservesWindowsBackslashPaths(核心回归),
          PreservesUNCPath, UNCPrefixWithEscapedBackslashes,
          PreservesWindowsPathWithSpace, StillSupportsEscapedQuotes,
          MixedSeparators, TrailingBackslashBeforeQuoteIsAmbiguous,
          RejectsUnterminatedQuote。
    状态: [x] 已完成

[15] main.go:2553 randomToken 用时间戳做伪随机种子

第 4 节  流水线性能优化 (用户要求: 全部使用 CPU, 在服务器 Docker 中运行)
================================================================================

背景: 用户询问"流程都是啥步骤, 为什么有的步骤运行慢"。基于真实 job 记录
      runtime/jobs/1790051120838202276-9wj6dc (428 张影像 / 2.76 GB) 逐条还原
      日志时间戳, 得到实测耗时, 而不是估算:

        影像预处理            2.5 秒
        特征提取          1,428.6 秒 (23.8 分钟)
        特征匹配          单块 79~311 秒, 平均 252 秒/块
                          COLMAP 把 428 张切成 9x9=81 块
                          已完成 24 块时已耗 6,057 秒 (1.7 小时)
                          线性外推全部 81 块约 5.7 小时

      结论: 慢的不是 OSGB 阶段, 而是 COLMAP 前段, 且有两个可量化的根因。

--- [20] 特征匹配使用穷举匹配 (O(n^2)) — 最大浪费 -------------------------
    问题: 代码硬编码 exhaustive_matcher, 428 张图产生 428*427/2 = 91,378 个
          图像对。航飞影像按航线顺序拍摄, 只有相邻帧才可能重叠, 穷举搜索
          绝大部分是无用功。
    修复: 新增 COLMAP_MATCHER 配置(默认 sequential), 支持
          sequential / exhaustive / vocab_tree / spatial / transitive;
          未知值安全回退到 exhaustive(永远正确, 只是慢)。
          sequential 支持 COLMAP_MATCHER_OVERLAP(默认 10)。
          实测候选图像对: 91,378 -> 4,280, 减少 95%。
          两版本 COLMAP 均确认支持 --SequentialMatching.overlap:
          - 本机 4.2.0 (CUDA) 与容器 3.9.1 均有该选项。
    状态: [x] 已完成

--- [21] 线程数硬编码为 4, 浪费绝大多数 CPU --------------------------------

          --num_threads 4, OpenMVS 稠密重建写死 --max-threads 4。
          本机 32 逻辑核, 相当于只用 12.5% 算力。

          image_undistorter、ReconstructMesh、RefineMesh、TextureMesh。
          OpenMVS 的 --max-threads 已从 .env.example / compose.yaml 的

--- [23] COLMAP 4.x 选项组改名导致特征提取/匹配必然失败 (严重) ----------------
    问题: 这是本次分析中最重要的发现, 是真实功能性缺陷。
          COLMAP 在 4.0 把 SIFT 处理相关选项从
            --SiftExtraction.* / --SiftMatching.*
          改名为
            --FeatureExtraction.* / --FeatureMatching.*
          且两组拼写互斥 —— 传错是硬错误("unrecognised option"), 直接退出,
          不是警告。实测两个真实二进制:
            本机 COLMAP 4.2.0 (with CUDA)
              --SiftExtraction.use_gpu 0  -> FAILED, exit 1
              --FeatureExtraction.use_gpu 0 -> 正常
            容器 COLMAP 3.9.1 (without CUDA, 部署目标)
              --SiftExtraction.use_gpu 0  -> 正常
              --FeatureExtraction.use_gpu 0 -> FAILED
          原代码写的是 --SiftExtraction.*(提取) 与 --SiftMatching.*(匹配):
            - 在部署容器 3.9.1 上恰好可用, 所以 Docker 里看不出问题
            - 但 --SiftMatching.use_gpu / num_threads 在 4.2.0 上不存在
              (4.2.0 的 SiftMatching 组只剩 max_ratio / max_distance /
               cross_check 等参数), 因此在 4.x 上特征提取必然失败
            另注: 真实日志显示两次运行之间匹配参数被改过
              (run1 用 --FeatureMatching.*, run2 用 --SiftMatching.*),
              说明这一点此前被反复试错而未定型。
    修复: 新增 cmd/server/colmap_args.go, 运行时探测而非硬编码版本号:

              `colmap feature_extractor --help`, 检查输出里出现的是

              而参数每次建任务都会重建)
            - 探测失败(二进制不存在/help 不支持)安全回退到 legacy 拼写,
              因为固定部署镜像用的是 3.9.1
            - 选择依据是"问二进制"而不是解析版本字符串: --help 输出格式
              在版本间变化过, 猜错会让任务跑到中途才失败

            现代: feature_extractor ... --FeatureExtraction.use_gpu 0

                  sequential_matcher ... --FeatureMatching.use_gpu 0
                  --FeatureMatching.num_threads N --SequentialMatching.overlap 10

    一度怀疑是新增的 --SequentialMatching.overlap 参数所致。
    经隔离测试确认: 加/不加该参数都会崩溃, 因此与本改动无关。
    真实原因是测试图过于退化(纯色小块, 10 张图只提取出 10 个关键点,
    平均每张 1 个), COLMAP 3.9.1 在特征数近零时自身断言失败。
    改用带纹理的图后 matching 正常产出 45~42 组匹配。
    已排除该误报, 未对代码做相应"修复"。
